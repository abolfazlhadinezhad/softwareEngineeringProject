# Backup and recovery

`scripts/backup.ps1` runs mysqldump inside MySQL with a consistent transactional snapshot, copies SQL without PowerShell text redirection, archives private media inside the application container and prints SHA-256 hashes. It does not reset/delete any volume. Defaults write to ignored `backups/`; pass a restricted destination and production Compose file if operating an authorized deployment. Stop or quiesce writes for a mutually consistent database/file snapshot; a transactional SQL dump alone does not coordinate uploads.

`scripts/restore-database.ps1` copies a verified SQL file and restores through container stdin redirection. It refuses to run without `-ConfirmRestore`. A restore changes existing records, so target identification, explicit operator authorization and a fresh backup are mandatory. Restore tests must use an isolated Compose project/database/media volume. No restore was performed against this development or any production database in this milestone. Backup/restore procedures are documented and implemented scripts, not a verified disaster-recovery claim.

University IT must approve backup frequency, encryption keys, off-site access, retention and RPO/RTO. Proposed starting discussion: daily encrypted backups plus pre-migration snapshots and periodic restore drills; no institutionally approved interval is asserted. Never store backups in Git or unrestricted shares. Media and database are both necessary; Redis contains disposable cache/queue state, while outstanding jobs should be reconciled from MySQL after recovery.

Recovery drill: create isolated project and credentials; verify dump/archive hashes; restore database into that target; restore media archive into its private-media volume using the same numeric application owner; apply compatible migrations; run integrity counts and synthetic login/download/ticket checks; compare recorded counts/files; record elapsed time and results; then explicitly authorize removal of only that isolated test environment. Do not use `down -v` against the live project.

Migrations use staged UUID backfill for existing tickets and additive schema changes. MySQL DDL is not generally transactionally reversible; take a pre-release backup. Review migration SQL and data backfills first. Rolling back an image is safe only when it supports the current schema; destructive schema reversal requires a separate approved recovery plan. Keep prior images and backup manifests.
